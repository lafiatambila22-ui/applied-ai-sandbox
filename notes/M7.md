# M7 — Multi-Tool Workflows

## Feature I picked
- Note search: a free-text filter bar on the home page that filters notes by title and body.

## Plan from chat
Data model changes: no changes to the note dict shape needed. Search is a read-only filter applied at render time.

Route changes: update the home route in app.py to accept an optional query param (q). If q is present, filter app.notes to only notes where q appears in the title or body (case-insensitive). Pass q back to the template so the input stays populated.

UI changes: add a search input at the top of home.html above the notes list. The form uses GET so the query appears in the URL and is bookmarkable. Add a small "clear" link next to the input.

Edge cases: empty string should return all notes. Case sensitivity should be ignored. Notes with no match should show a "no results" message instead of an empty list.

## Execute in Claude Code
- Branch: m7-note-search
- One thing Claude flagged that the chat plan missed: the search input needs to be outside any existing form tag in home.html or it will conflict with the delete forms already on the page.

## Polish with Copilot
- Renamed the variable q to search_query in app.py for clarity, Copilot suggested it as I started typing.
- Added a docstring to the home route explaining the optional search_query param, Copilot completed it after the first line.

## Review in chat
- The reviewer flagged that searching with a very long string has no length limit, which could cause slow renders on large note lists. Added a maxlength attribute to the search input to cap it at 100 characters.

## Parallel sessions
- Second task: added a note count line at the top of the home page showing "Showing X of Y notes" when a search is active.
- Worktree path: ../sandbox-task-b
- Honest answer: one session mostly sat idle while I was reviewing the other. True parallelism would need two monitors or at least two clearly separated terminal windows. I spent more time switching context than I saved.

## Workflow retro
The four lanes worked well as a structure for this feature. Chat handled the design and I got a clean one-page plan without any code getting written too early. Claude Code took that plan and implemented it in one focused session with a tight brief. Copilot handled the two small polish edits faster than I could have briefed an agent to do them. Chat reviewed the diff and caught the missing input length limit which was a real issue.

The place where one tool caught something another missed was the review step. Claude Code was focused on making the feature work and did not think about edge cases in the input. The chat reviewer had no investment in the code and spotted it immediately. That is the highest value step in the loop and I would not skip it on a real PR.

If I redid this feature I would write the acceptance criteria more carefully in the chat design step. I had to add the "no results" message myself because I forgot to include it in the brief. That is a context engineering miss, not a tool miss.

I spent the most time as the conductor during the handoff from chat to Claude Code, making sure the brief captured the design accurately. That was the right place to spend time. A bad handoff would have sent Claude Code in the wrong direction and cost more time to fix than it took to write the brief carefully.
