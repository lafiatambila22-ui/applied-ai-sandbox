# M7 — Multi-Tool Workflows

## Feature I picked
- Note search: a free-text filter bar on the home page that filters the notes list by title and body.

## Plan from chat
Data model changes: none needed. Search is a read-only filter applied at render time. Route changes: update the home route to accept an optional q query param and filter app.notes case-insensitively. UI changes: add a GET search form above the notes list with a clear link. Edge cases: empty string returns all notes, no results shows a distinct message.

## Execute in Claude Code
- Branch: m7-note-search
- One thing Claude flagged that the chat plan missed: the search input needs to be a standalone form tag and not nested inside any existing form on the page or it will conflict with the delete forms.

## Polish with Copilot
- Renamed the variable q to search_query in app.py for clarity.
- Added a docstring to the home route explaining the optional search_query param.

## Review in chat
- The reviewer flagged that the search input had no length limit, which could cause slow renders on large note lists. Added maxlength="100" to the input.

## Parallel sessions
- Second task: added a note count line showing "Showing X of Y notes" when search is active and "X notes" otherwise.
- Worktree path: ../sandbox-task-b
- Honest answer: one session mostly sat idle while I was working in the other. True parallelism would need two monitors or clearly separated terminals. I spent more time switching context than I saved, but I can see how it would help on longer tasks.

## Workflow retro
For this feature I used four tools across four distinct lanes. Chat handled the design upfront and produced a clean one-page plan without any code getting written too early. Claude Code took that plan and implemented it in focused sessions with tight briefs. Copilot handled small polish edits like renaming variables and adding docstrings faster than I could have briefed an agent. Chat reviewed the final diff and caught a missing input length limit that the implementing agent missed.

The place where one tool caught something another missed was the review step. Claude Code was focused on making the feature work and did not think about edge cases in the search input. The chat reviewer had no investment in the code and spotted the missing maxlength attribute immediately. That is the highest value step in the loop and I would not skip it on a real PR.

If I redid this feature I would write the acceptance criteria more carefully in the chat design step. I had to go back and fix the no results message and the search input value staying populated because I forgot to include those in the brief. Those were context engineering misses not tool misses.

I spent the most time as the conductor during the handoff from chat to Claude Code making sure the brief captured the design accurately. That was the right place to spend time. The parallel sessions step showed me that true parallelism needs more intentional setup. On a longer running task where one agent is doing heavy work it would save real time.
